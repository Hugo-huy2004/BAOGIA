## Problem Statement

Hugo Studio already has an app-oriented home, widgets, Spotlight, a Library and a broad catalog, but the catalog feels uneven: some apps have real server-backed depth while others still feel like isolated utilities or UI experiments. A Daily Quest-first redesign would remove the exploratory character the founder values and make strong apps subordinate to one workflow.

The destination is **HugoOS App Universe**: a free, smooth ecosystem for high-school and university students where Hugo Studio owns the platform, every mature app can become a deep product with its own UI and domain, and shared infrastructure preserves identity and context across apps.

Primary user: the **Student Builder** — a student who studies, joins clubs or teams, and creates technology or creative projects that can become a credible portfolio.

## What Makes This Cool

HugoOS behaves like a **Living Campus**:

- Hugo Home is the central plaza: apps, widgets, dock, Library and Spotlight remain the front door.
- Each app is a distinct building with its own atmosphere, workflows and product depth.
- The Kernel is invisible. Identity, installation state and a few canonical objects follow the user without flattening app identity.
- A server-verified learning result can appear privately in Profile without duplicate entry.
- Hugo Studio can keep launching experiments, but only mature apps receive **Hugo Studio Verified** status.

> A launcher opens apps. HugoOS lets identity and work continue across apps.

## Constraints

- Keep the current App Home, Library, widget, icon, dock and Spotlight mental model.
- Daily Quest is an optional app/widget, never the mandatory home or organizing principle.
- Free core access is not gated by Hugo Store. Store is limited to optional supporter products, merchandise and benefits.
- Runtime remains a React/Vite PWA with Node/Express/Mongoose on port 8099. The browser talks only to Node for `/api/*` and `/ws*`; Python remains server-to-server.
- V1 stays inside the existing frontend and backend deployments. Boundaries are in-process modules and data contracts, not microservices.
- V1 is online-first. It does not attempt generic offline mutation sync, generalized permission infrastructure or object search.
- The repository currently has lint/build/performance checks but no broad test suite. V1 virtual staff are observation-only.
- Public evidence, team evidence, JOY integration, new apps and upgrades to HugoPSY/Cinema/Radio are outside V1.

## Premises and Decisions

- “OS” initially means a shared product and data platform, not a native operating-system kernel.
- More apps are welcome, but breadth cannot excuse shallow apps.
- Server strength means canonical authenticated state, validation, migrations, observability and recovery—not one server per app.
- Each app owns its workflows and presentation. A shared record has one authoritative owner; consumers query it rather than copy it.
- V1 proves the architecture with one vertical slice before generalizing it.

## Cross-Model Design Perspective

Two independent design reads converged on **Living Campus / One OS, many worlds**:

- Home is a plaza and apps have distinct visual “climates.”
- Brand and app depth come first; the Kernel stays invisible during normal use.
- The dock can become a persistent cross-world navigation spine.
- Shared system surfaces include account, loading/error states and command palette; app accent, illustration, motion metaphor and information density may differ.

Provisional direction for a later design review, not a V1 engineering dependency: Be Vietnam Pro for display, Inter Variable for UI, JetBrains Mono for code/data; warm `#F7F6F2`, dark `#101218`, Hugo accent `#715CFF`, positive accent `#B9F227`; shared 4 px spacing and 120/220/360 ms motion rhythms.

## Approaches Considered

- **Quest Overlay — rejected:** preserves duplicated foundations and makes Quest too central.
- **HugoOS Kernel — selected:** shared platform runs behind the current App Home and deep app environments.
- **Student World — not selected as architecture:** its language may inspire design, but mandatory game framing would narrow usefulness.

## Destination Architecture

```text
Hugo Home / Library / Spotlight / Dock / Widgets
                         ↓
               Versioned App Contract
                         ↓
Identity · Registry · Permissions · Shared references · Notifications · JOY
                         ↓
 Study | Team | Profile | Wallet | Invest | Cinema | Radio | Arcade | Aura | New apps
```

This is the destination. V1 implements only Registry/layout state and one private Study → Profile evidence flow.

## V1 Scope: Registry + Private Study Evidence

### Included

1. One source-controlled App Manifest Registry consumed by Home, Library and Spotlight through one API.
2. Existing member Bio fields become the canonical server layout; browser storage becomes cache/migration input only.
3. App Manifest v1 validation for current apps.
4. One canonical `LearningEvidence` record created by the trusted Study completion module and rendered privately by Profile.
5. L0 Server Specialist and UI Specialist summaries using existing monitoring surfaces and Telegram.

### Explicit non-goals

- Generalized permissions, retention policies, HugoObject graph, Project or Achievement types.
- Generic offline writes, multi-master sync or search over user objects.
- Public/team evidence, guardian/age policy or Profile publication.
- Independent app deployments or app-specific code rollback.
- JOY, Team, Daily Quest, new apps or complete visual-system implementation.
- Automatic retry/restart/rollback of product infrastructure, patch generation or merging.
- Custom incident warehouse/dashboard or browser synthetics in production.

## V1 Ownership and Trust Boundaries

| Record | Canonical owner | Authorized mutation | Consumers |
|---|---|---|---|
| Manifest Registry | Registry module/source file | Release process after atomic validation | Home, Library, Spotlight |
| App layout | Authenticated member Bio | Registry routes using `requireMember` and `req.memberEmail` | Home, Library, Spotlight |
| Lesson completion | Study module | Existing authenticated/verified completion path | Study and Evidence function |
| LearningEvidence | Evidence module/collection | Trusted in-process Study function creates; owner route deletes | Private Profile query |

“Study module” and “Profile module” are code boundaries inside the Node monolith, not network identities. Route middleware authenticates the member. Internal functions accept the resolved member identifier; they never accept identity from client payloads.

## App Manifest v1

Manifests live in one source-controlled Registry module. CI validates the complete Registry atomically; the server also validates before reporting ready. Any invalid manifest rejects the entire new deployment, so the hosting platform keeps the previous monolithic release active. There is no partial last-known-good snapshot inside the new process.

`contractVersion` describes schema compatibility; `contentVersion` tracks app-visible configuration and does not imply independent deployment. V1 supports contract major `1` only.

### Required fields

| Field | Type/rule |
|---|---|
| `id` | lowercase string matching `^[a-z][a-z0-9_]{1,31}$`; stable and never reused |
| `name` | localized object with required `vi` and `en`, each 1–60 chars |
| `keywords` | localized object with `vi`/`en` arrays, max 20 strings of 1–40 chars |
| `contractVersion` | semver; V1 accepts `1.x` |
| `contentVersion` | semver |
| `owner` | Hugo Studio owner string |
| `maturity` | `experimental`, `beta`, `verified`, `system` |
| `installPolicy` | `required` or `optional` |
| `routes.home` | internal absolute path |
| `routes.deepLinks` | array of allowed internal path patterns; may be empty |
| `capabilities` | array from `widget`, `spotlight`, `learningEvidenceProducer`; may be empty |

Unknown fields and unknown enum values are rejected. Duplicate IDs, invalid/internal-route escapes and unsupported contract majors fail validation. `maturity` never controls uninstall; `installPolicy` does.

```json
{
  "id": "study",
  "name": { "vi": "Hugo Study", "en": "Hugo Study" },
  "keywords": { "vi": ["học", "bài học"], "en": ["study", "lesson"] },
  "contractVersion": "1.0.0",
  "contentVersion": "1.0.0",
  "owner": "hugo-studio-learning",
  "maturity": "beta",
  "installPolicy": "optional",
  "routes": {
    "home": "/member/utilities/study",
    "deepLinks": ["/member/utilities/study/lessons/:lessonId"]
  },
  "capabilities": ["widget", "spotlight", "learningEvidenceProducer"]
}
```

`learningEvidenceProducer` is static release metadata, not a member-granted permission. Only a hard-coded Study module call path is authorized in V1; other manifests cannot gain write authority merely by declaring the capability.

## Canonical App Layout

V1 reuses the existing one-Bio-per-member server record instead of introducing another account-state collection.

```text
Bio.installedUtilities: string[]        // normalized set order
Bio.homeScreenUtilities: string[]       // ordered subset of installedUtilities
Bio.utilitySizes: Map<appId, small|medium|large>
Bio.hugoSOCompletedSteps: string[]       // imported legacy HugoSO step IDs
Bio.appLayoutRevision: integer          // default 0; covers all three fields
Bio.appMigrationDevices: [{ deviceIdHash, importedAt }] // capped at 20
Bio.appLayoutLegacySnapshot: { installed, home, sizes, revision, expiresAt } | null
```

The existing unique member identity/Bio lookup remains the uniqueness boundary. Every mutation uses one atomic `findOneAndUpdate` against `{ email: req.memberEmail, appLayoutRevision: expectedRevision }`. Home IDs must be unique, known, installed and permitted by `installPolicy`. Required apps are always normalized into installed state and cannot be removed. Utility-size keys outside the installed set are discarded.

### Install meaning

In this PWA, install means account state, not a native package download:

- the app appears Installed in Library;
- it may be pinned/ordered on Home;
- declared widget and Spotlight entries become eligible;
- service-worker caching remains usage-driven.

Uninstall removes installed/Home/widget/Spotlight presence. It does **not** delete app-domain data in V1. Account deletion continues through the existing account-deletion path; per-app data deletion is a later design.

## Registry/Layout API v1

All responses use:

```json
{ "data": {}, "requestId": "..." }
```

Errors use:

```json
{ "error": { "code": "REVISION_CONFLICT", "message": "...", "details": {} }, "requestId": "..." }
```

| Endpoint | Request | Success |
|---|---|---|
| `GET /api/apps` | none | `{ registryVersion, layoutRevision, homeAppIds, utilitySizes, apps[] }` |
| `PUT /api/apps/:id/install` | `{ expectedRevision, pin }` | complete updated layout; exact desired-state replay is a no-op success |
| `PATCH /api/apps/layout` | `{ expectedRevision, homeAppIds, utilitySizes }` | complete updated layout |
| `DELETE /api/apps/:id/install` | `{ expectedRevision }` | complete updated layout; already-uninstalled optional app is a no-op success |
| `POST /api/apps/migrate-v1` | migration payload below | `{ imported, ignored, conflicts, layout }` |

`registryVersion` is the SHA-256 of normalized manifest bytes. `apps[]` contains the public manifest fields plus `{ installed, pinned, homeOrder }`. Registry size is bounded by the source file, so V1 has no pagination. PUT/DELETE first compare the requested desired state with canonical state: an exact no-op returns success even when `expectedRevision` is stale; any real mutation with a stale revision returns `409 REVISION_CONFLICT` with current layout. Other codes: `400 INVALID_INPUT`, `401 UNAUTHENTICATED`, `403 REQUIRED_APP`, `404 APP_NOT_FOUND`, `429 RATE_LIMITED`.

PUT/DELETE are naturally idempotent against current canonical state; V1 does not build a generalized idempotency-key store.

## Legacy Migration and Rollback

Exact migration sources:

- server: `Bio.installedUtilities`, `Bio.homeScreenUtilities`, `Bio.utilitySizes`;
- browser: the existing installed-app, Home-app and utility-size keys used by `MemberUtilitiesDashboard`;
- Study: existing member `completedLessons` plus local `hugoso_completed_steps_v1`.

Payload:

```json
{
  "deviceMigrationId": "random-128-bit-value",
  "installedAppIds": ["study", "profile"],
  "homeAppIds": ["study"],
  "utilitySizes": { "study": "large" },
  "studyCompletedIds": ["lesson12"]
}
```

The client generates and persists `deviceMigrationId`; the server stores only its SHA-256. That hash is the migration dedupe key, so this endpoint accepts neither `Idempotency-Key` nor a client `expectedRevision`. The server owns migration concurrency.

Layout fields, existing `completedLessons` and the new `hugoSOCompletedSteps` all live on the same Bio document. One conditional `findOneAndUpdate` therefore commits the layout and progress merge atomically without a cross-collection transaction. One server-owned retry loop performs the migration:

1. Load Bio and revision; if device hash exists, return the current layout.
2. Filter unknown apps/steps, normalize required apps and merge installed IDs by union.
3. Existing nonempty server Home order wins; otherwise accept the first valid client order. Append missing valid installed apps only when requested as Home apps.
4. Partition known `studyCompletedIds` into existing `completedLessons` and `hugoSOCompletedSteps`, then merge each by set union. Legacy progress does not generate evidence because it was not server-verified through the new completion path.
5. Atomically update layout/progress, increment revision and append device hash. A revision race retries from the new state up to three times, then returns `409`.
6. Return accepted, ignored and conflicted items. A never-reopened device cannot be discovered; release notes disclose this limit.

Old and new code read the same three Bio layout fields, so compatibility is inherent and there is no second representation to dual-write. Before the first cutover mutation, store a server-side snapshot of those fields for audit and manual recovery only. Normal rollback disables the environment flag and deploys the previous release, which reads the latest compatible Bio values on every device. The snapshot may be restored only through an explicit admin recovery action if migration normalization itself corrupted a layout. Keep it for two releases, then remove it through a separately approved cleanup.

## LearningEvidence v1

The collection has a permanent unique index on:

```text
(ownerMemberId, sourceApp, source.type, source.id, kind)
```

Document fields:

```json
{
  "id": "opaque-server-id",
  "schemaVersion": 1,
  "ownerMemberId": "member-id",
  "sourceApp": "study",
  "source": { "type": "lesson", "id": "lesson12" },
  "kind": "lesson_completion",
  "title": "React State Foundations",
  "skillTags": ["react", "state-management"],
  "occurredAt": "2026-08-22T09:00:00Z",
  "proof": { "method": "server_verified_completion", "ref": "completion-id" },
  "status": "active",
  "createdAt": "2026-08-22T09:00:01Z",
  "updatedAt": "2026-08-22T09:00:01Z"
}
```

Only the trusted in-process Study completion function creates evidence. It receives the authenticated member ID from the route, verifies completion, then create-or-returns by the unique tuple. Duplicate completion returns the existing active record.

Owner deletion changes `status` to `deleted` and immediately scrubs `title`, `skillTags` and `proof`. The minimal owner/source/kind tombstone remains permanently to prevent recreation; future completion attempts return `410 EVIDENCE_DELETED`. Uninstalling Study or Profile does not delete evidence. Full account deletion removes the evidence/tombstones through the existing account-deletion workflow.

Endpoints:

```text
POST /api/study/lessons/:lessonId/complete
  → authenticated Study validation
  → in-process Evidence.createOrReturn(memberId, completion)
  → private evidence DTO

GET /api/profile/me/evidence?cursor=<opaque>&limit=20
DELETE /api/profile/me/evidence/:id
```

`limit` defaults to 20 and caps at 50. The private allowlisted DTO is exactly `{ id, kind, title, skillTags, occurredAt, sourceApp, source, status }`; it excludes `ownerMemberId` and `proof.ref`. There is no public endpoint or visibility mutation in V1. Owner routes use `requireMember` and match `req.memberEmail` to the canonical member ID.

## V1 Spotlight

Spotlight performs Unicode-normalized exact/prefix matching over validated Registry `id`, localized `name` and localized `keywords`, then filters by member/app availability. It returns at most 20 apps. It never indexes LearningEvidence or other user data.

## Feature Flags and Pilot

V1 uses two server environment flags, default `false`: `HUGO_APP_REGISTRY_V1` and `HUGO_LEARNING_EVIDENCE_V1`. Production pilot access additionally requires the authenticated member ID to appear in a server-only `HUGO_V1_PILOT_MEMBER_IDS` allowlist. The allowlist is never returned to clients; APIs fail closed to the legacy behavior/404 when disabled. The frontend renders only capabilities returned by authenticated bootstrap/API responses. Staging may enable both flags globally.

## Test and CI Strategy

Adding these checks requires explicit owner approval because the repository currently has a no-broad-tests convention.

- **API/service checks:** Node built-in `node:test`, existing Express modules and a disposable Mongo database supplied by `MONGODB_TEST_URI`; GitHub Actions provides the Mongo service. A seeded member and signed test JWT exercise real `requireMember` middleware. No test-only auth route exists in production.
- **Browser checks:** the existing `@playwright/test` dependency starts the frontend/Node against the disposable database. Global setup seeds the member and creates a cookie with a CI-only JWT secret. Run Chromium desktop plus an Android-like mobile viewport; Safari/WebKit and physical-device coverage remain manual release checks.
- **CI:** a separate HugoOS V1 job runs manifest validation, Node integration checks and two Playwright journeys without changing the current general test policy for unrelated domains.

Required checks:

1. Atomic manifest validation and incompatible-version rejection.
2. `requireMember`, ownership and client-identity spoof rejection.
3. Atomic install/layout revision conflict and required-app behavior.
4. Multi-device migration dedupe, union rules and three-retry conflict behavior.
5. Permanent evidence dedupe plus delete/scrub/410 behavior.
6. Playwright: legacy import → install/pin → second authenticated browser context sees canonical layout.
7. Playwright: complete new Study lesson → exactly one private Profile evidence → delete → no display/recreation.

## Quality and Performance Gate

- Automated UI: Chromium desktop 1440×900 and mobile 390×844.
- Manual release: iOS 16+ Safari/PWA, Android 10+ Chrome/PWA on a 4 GB reference device, and latest two major Chrome/Edge/Safari desktop.
- Network: lab Fast 3G plus normal 4G/Wi-Fi; failed mutations must show retry/conflict instead of false success.
- Accessibility: WCAG 2.2 AA for V1 Home/Library and Study → Profile flows.
- Shell lab target: median of five cold mobile runs has LCP below 2.5 s; interaction checks remain below 200 ms where measurable.
- API load profile: 20 concurrent seeded members for five minutes, 95% Registry/evidence reads and 5% layout/completion writes, 20 manifests and 100 evidence rows/member. p95 read latency target is below 500 ms with error rate below 1%.

V1 code is one monolithic release. Code rollback is whole-release. Capability flags contain Registry/evidence behavior; no document promises independent app rollback.

## Virtual Quality Staff — V1 L0

V1 reuses rather than builds a monitoring platform:

- Server Specialist consumes structured Node logs, existing operations routes/aggregates and one Cloudflare Worker API probe for authenticated staging health.
- UI Specialist consumes existing `ClientMetric`/client-monitoring aggregates and Playwright CI/manual staging reports. Cloudflare does not pretend to run browser journeys.
- A confirmed server incident is three consecutive 30-second probe failures or more than 5% failures with at least 20 requests in five minutes for the same route/release.
- From confirmation—not first failure—the Telegram Bot API delivery target is two minutes. Delivery alone may retry three times with bounded backoff; this is notification transport, not product remediation. Existing operations data is the fallback if Telegram fails.
- Telegram summaries contain severity, release, route/app, aggregate impact, redacted evidence and a suggested manual containment step.

No automatic product remediation or infrastructure recovery is authorized in V1. L1 runbooks, L2 patch generation and L3 auto-merge require later designs plus tests and staging drills. Balances, auth, permissions, schemas and irreversible user data never qualify for unattended changes.

## Hugo Studio App Standard

The 100-point standard is a destination, not a V1 software subsystem. A release owner evaluates an app from automated output, live QA, performance/accessibility report and privacy/security checklist. Verified requires at least 80/100 and no critical security, data-loss, accessibility or broken-core-flow blocker.

| Dimension | Weight | Evidence |
|---|---:|---|
| Recurring user outcome | 20 | Observation/task completion |
| Server/data integrity | 20 | Contract/auth/migration checks |
| UI completeness | 20 | Mobile/desktop states and QA |
| Reliability/performance | 15 | Load and monitoring evidence |
| Useful ecosystem continuity | 15 | Demonstrated non-artificial cross-app flow |
| Safety/privacy/i18n | 10 | Signed checklist and accessibility report |

Each published subcriterion is scored 0–5 and normalized to its weight. The release owner records evidence and rationale. Written overrides may adjust noncritical scores but never bypass critical blockers. A focused app may excel at one recurring workflow; the standard does not require artificial feature count or integration.

## Milestones and Go/No-Go Gates

### M0 — Approval, harness and baseline

- Approve V1 scope and addition of the isolated Node/Playwright checks.
- Define telemetry retention/redaction and name pilot members/reference device.
- Add disposable Mongo/seed/auth-fixture design to CI and capture current metrics.
- **Go:** test job passes against current baseline; flags fail closed. **No-go:** public evidence, generic permissions/search/sync or new apps re-enter V1.

### M1 — Registry shadow mode

- Atomic manifest validator, Registry read API and migration dry-run report.
- Home/Library/Spotlight compare Registry output with current output without changing users.
- **Go:** all current app IDs map; ignored/conflicted legacy values are explained.

### M2 — Layout cutover

- Revisioned Bio layout API, same-document atomic migration, compatibility rollback window and complete conflict UI.
- **Go:** tests 1–4 and cross-context layout E2E pass; pilot sees no unexplained loss/order change.

### M3 — Private Study evidence

- Evidence collection/function, Study completion hook, private Profile list and delete/scrub behavior.
- **Go:** test 5 and evidence E2E pass; no public/team route exists.

### M4 — L0 reporting and limited release

- Existing metrics/logs wired to two specialist summaries; API probe and Telegram delivery drill.
- **Go:** manual QA/a11y/privacy artifacts signed; delivery/fallback drill passes.

### M5 — Observe before generalizing

- Measure task completion, migration problems, Profile evidence usefulness and week-later return intent in a limited cohort.
- **Go to V2:** students use the slice without assistance and observations justify the next app/object.

## V1 Success Criteria

- Home, Library and Spotlight consume one validated Registry; duplicated runtime catalog/version/storage sources are retired after the rollback window.
- Canonical Bio layout follows the member across two authenticated browser contexts and handles stale revisions visibly.
- A newly verified Study lesson creates exactly one active private evidence record; Profile renders only the allowlisted DTO.
- Delete removes private display, scrubs content and permanently prevents accidental recreation.
- All seven required checks, including both E2E journeys, pass; manual browser/device and WCAG gates are signed.
- Lab/load targets pass with complete loading, empty, error, conflict and retry UI states.
- Confirmed staging incidents reach Telegram within two minutes of confirmation, and failed delivery remains visible through existing operations data.
- Five observed student testers complete layout plus Study → Profile flow without assistance; at least three explain a reason to reuse Study or Profile the following week.

## Distribution Plan

HugoOS remains the current web/PWA deployment. V1 ships behind server-default-off environment flags through the existing frontend/Node artifacts. Staging enables flags globally; production enables only the server-side pilot allowlist. Registry manifests are validated atomically in CI/startup. Whole-release rollback, shared backward-compatible Bio fields and the temporary audit snapshot provide containment.

## After V1 — Non-binding Direction

- Upgrade Profile/Passport, Aura sync, Team projects/clubs and the rest of Study based on observed use.
- Add Project or Achievement only when two real apps need each object.
- Introduce public/team evidence only after a separate age, consent, revocation and audit design.
- Add L1 safe runbooks only after staging drills; L2/L3 need later security/engineering review.
- New App Lab candidates: Career Lab first, then Knowledge, Campus Events or Student Money, one at a time.
- Explore dock-led world transitions and Kernel X-ray in a dedicated visual review.
